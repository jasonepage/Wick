# wick-api — Wick 3.0 live-multiplayer backend (phase 1, FREE)

Server-side system for Wick 3.0: **free live head-to-head** (Race = Duel), matchmaking
(random queue + friend codes), disclosed **bot** fill for empty queues, and the `/d/:code`
OG share preview. The forward-looking cross-platform design note is `docs/wick/CROSS_PLATFORM.md`.

**Phase 2 (Pro — NOT built here):** `POST /keeper` LLM proxy, ranked, cosmetics,
StoreKit entitlement. The seams are left in place (mode carries `"ranked"`; ranked never
bot-fills) but no Pro code exists yet.

Stack: Node + Hono + TypeScript + `ws`, single warm Render Starter instance, in-memory
rooms/queue, **no database of secrets or users** (C1/C2). Provisioned by the root
`render.yaml` Blueprint (this service is `rootDir: wick-api`).

## Layout

| File | What |
|---|---|
| `src/room.ts` | Authoritative match state machine — clock/solve/win/timeout/disconnect (FR-8/11/17/31/32/33). Pure; inject `now`. |
| `src/matchmaker.ts` | Random-queue pairing + friend-code rooms + bounded-wait bot-fill (FR-9/13/15). Pure. |
| `src/bot.ts` | Deterministic, seeded algorithmic opponent with human-like pacing (FR-13). |
| `src/preview.ts` | Port of `DuelCode.swift` → non-revealing OG preview (FR-5, FR-30). Never yields a word. |
| `src/protocol.ts` | WS `/match` wire frames + parser (SDS §4). |
| `src/hub.ts` | Runtime glue: matchmaker → room → bot, transport-agnostic. Injectable clock. |
| `src/words.ts` | Placeholder multiplayer word pool (NOT single-player daily words). |
| `src/server.ts` | Runnable service: `GET /healthz`, `GET /d/:code`, `WS /match`, tick loop. |

## Endpoints

- `GET /healthz` → `{ ok: true, ... }` (FR-1).
- `GET /d/:code` → OG-tagged HTML preview; decodes legacy `WK-`/`WR-` codes but never
  reveals a word; **never 404s** on a bad code (FR-5, FR-30/OD-7).
- `WS /match?kid=<appAttestKeyId>` → live match. Client frames: `queue`, `guess`,
  `question`, `heartbeat`. Server frames: `paired`, `state`, `result`, `opponentLeft`,
  `error`.

## Develop

```bash
npm ci
cp .env.example .env   # then put your own Gemini key in GEMINI_API_KEY
npm test          # vitest — pure logic + preview parity + hub e2e
npm run typecheck # tsc --noEmit
npm run build     # tsc → dist/
npm run dev       # tsx watch (local); or: npm start (runs dist/)
```

Both `npm run dev` and `npm start` load `.env` if it exists (Node `--env-file-if-exists`,
Node 22.9 or newer). Every variable is documented in `.env.example`. `GEMINI_API_KEY` is
the only one you need; without it the server runs with a rough lexical fallback for warmth
and no Keeper. On a host like Render, set the variables in the dashboard instead.

Preview parity is proven against **canonical vectors generated by the app's own
`debug/duel_tracer.py`** (`src/duelcode.vectors.json`) — so shared links decode identically
to the shipped Swift. Regenerate if `DuelCode.swift` ever changes.

## Server-authoritative model (C8)

The server holds the match secret (a *multiplayer* word, never a single-player daily word —
C1 intact) and verifies solves by exact normalized match, stamping the solve time from its
own clock. That decisive path is not client-forgeable. **Warmth** (hot/cold) is a semantic
value only the on-device engine can produce; the server can't recompute it, so warmth is
client-reported and used only for the live opponent strip and the *timeout* tie-break.

## Open decisions hit while building (defaults applied; not yet confirmed)

- **OD-1** win condition / tie-break — first-to-solve; timeout → warmest best guess; tie = draw.
  Caveat: tie-break-by-warmth is the one client-influenceable outcome (see above). If it must
  be cheat-proof, switch to a server-observable signal (e.g. fewest guesses).
- **OD-2** unlimited free in-match guesses/questions — implemented.
- **OD-3** 5-min cap; ~10s wait before bot — implemented as defaults.
- **OD-4** **bots first** (ghost replay deferred; no trace data yet) — `ghoststore` not built.
- **OD-8** ~15s reconnect grace before forfeit/void — implemented.
